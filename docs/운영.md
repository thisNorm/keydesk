# Keydesk 운영 안내

Keydesk는 한 명이 한 서버에서 운영하는 API 키 보관함입니다. 이 문서는 로컬 설치, 업데이트, 백업과 복구, Docker 운영을 설명합니다. 처음에는 보관함을 로컬에서 사용하고, 이후 필요한 경우 SMTP와 게이트웨이를 추가하세요.

## 설치와 첫 실행

Node.js 26.12.1과 npm 11 이상을 설치하세요. Windows에서는 PowerShell 5.1 이상, macOS와 Linux에서는 기본 터미널을 사용할 수 있습니다. 프로젝트와 데이터 경로에는 한글과 공백을 사용할 수 있습니다.

프로젝트 디렉터리에서 다음 명령을 실행하세요.

```sh
npm ci
npm run setup
npm run build
npm start
npm run status
```

`npm ci`는 고정된 의존성을 설치합니다. `setup`은 저장소와 초기 설정 토큰을 준비하며 토큰을 출력하지 않습니다. `start`는 백그라운드에서 서버를 실행하고 실제 HTTP 준비 상태를 확인합니다. `status`가 준비되지 않았다고 표시하면 데이터 디렉터리의 `server.log`를 확인하세요.

기본 접속 주소는 <http://127.0.0.1:8088>이고 데이터 디렉터리는 `.local/keydesk`입니다. 첫 설정 화면에서 토큰 파일을 직접 확인해 입력하세요.

PowerShell:

```powershell
Get-Content .local\keydesk\bootstrap-token
```

macOS와 Linux:

```sh
cat .local/keydesk/bootstrap-token
```

토큰을 확인하는 이 명령은 비밀값을 사용자의 터미널에 표시합니다. 화면 공유와 터미널 기록에 주의하세요. 계정 설정을 완료하면 일회용 토큰을 다시 사용하지 못합니다.

화면에서 소유자 이름과 12자 이상의 비밀번호를 등록한 뒤 키 항목, 인증값과 각 만료일을 입력하세요. 날짜와 알림의 기본 시간대는 Asia/Seoul입니다. SMTP를 설정하지 않아도 앱 안에서 만료 알림을 확인할 수 있습니다. 메일이 필요하면 설정 화면에 SMTP 값을 입력하고 테스트 발송을 확인하세요.

Windows에서는 프로젝트와 데이터 폴더를 자신의 사용자 프로필 아래에 두고 파일 속성의 보안 탭에서 다른 일반 사용자의 접근을 제한하세요. macOS와 Linux의 새 데이터 디렉터리는 소유자만 접근하도록 생성됩니다. 기존 디렉터리의 권한은 직접 확인하세요.

## 데이터 경로와 포트

환경변수는 서버를 시작하는 터미널에서 지정하세요. `stop`과 `status` 등 관리 명령에도 같은 `KEYDESK_DATA_DIR`를 사용해야 합니다. 명령이 `.env` 파일을 자동으로 읽지는 않습니다.

| 환경변수           | 기본값                      | 용도                                                     |
| ------------------ | --------------------------- | -------------------------------------------------------- |
| `KEYDESK_DATA_DIR` | 프로젝트의 `.local/keydesk` | 영구 데이터 경로                                         |
| `KEYDESK_HOST`     | `127.0.0.1`                 | 서버가 수신할 주소                                       |
| `KEYDESK_PORT`     | `8088`                      | 서버 포트                                                |
| `KEYDESK_ORIGIN`   | `http://127.0.0.1:8088`     | 관리 화면의 정확한 접속 출처; 포트 변경 시 기본값도 변경 |

PowerShell:

```powershell
$env:KEYDESK_DATA_DIR = 'C:\Users\사용자\Keydesk 데이터'
$env:KEYDESK_PORT = '8089'
$env:KEYDESK_ORIGIN = 'http://127.0.0.1:8089'
npm start
npm run status
```

macOS와 Linux:

```sh
export KEYDESK_DATA_DIR="$HOME/Keydesk 데이터"
export KEYDESK_PORT=8089
export KEYDESK_ORIGIN=http://127.0.0.1:8089
npm start
npm run status
```

`KEYDESK_ORIGIN`에는 끝의 `/`와 경로를 붙이지 마세요. 기본 설정은 해당 기기에서만 접속할 수 있습니다. Windows PC와 맥북에 각각 설치하면 서로 다른 보관함이 만들어집니다. 여러 기기에서 같은 데이터를 사용하려면 한 서버에 접속해야 하며, 백업 복원은 자동 동기화가 아닙니다. SQLite 데이터 디렉터리를 클라우드 동기화 폴더나 공유 네트워크 드라이브에 두지 마세요.

## 시작, 중지와 업데이트

```sh
npm run status
npm run stop
```

중지 명령은 해당 데이터 디렉터리의 개인 제어 토큰을 확인한 실행 관리자에게만 요청합니다. 상태 파일의 PID만 보고 프로세스를 종료하지 않습니다. 다른 앱이나 별도 터미널에서 직접 실행한 서버를 강제로 종료하지 않습니다.

업데이트 전에는 암호화 백업을 만든 뒤 다음 순서로 진행하세요. 소스 업데이트는 사용하는 Git 브랜치와 검토한 버전에 맞게 수행하세요.

```sh
npm run stop
npm run backup -- --output "업데이트 전.keydesk"
# 검토한 새 버전으로 소스를 업데이트한 뒤 실행
npm ci
npm run build
npm test
npm start
npm run status
```

서버나 호스트를 다시 시작한 뒤에도 데이터 디렉터리는 그대로 사용하세요. 로컬 `npm start`는 로그인 또는 시스템 재부팅 때 자동 실행되는 서비스로 등록되지 않습니다. 상시 운영에는 아래 Docker의 재시작 정책이나 운영체제의 서비스 관리자를 사용하세요. 서비스 관리자가 `node apps/server/src/main.ts`를 직접 실행한다면 중지도 해당 서비스 관리자로 수행하세요.

## 백업과 복원

데이터 디렉터리에는 `keydesk.sqlite`, SQLite 보조 파일, `root-key`와 최초 설정용 `bootstrap-token`이 들어갑니다. `root-key`가 없으면 기존 암호화 값을 읽을 수 없으며 새 키로 대체하면 복구되지 않습니다. 원본 데이터 디렉터리를 보관할 때는 서버를 중지한 상태에서 루트 키와 데이터베이스 및 보조 파일을 함께 보호하세요.

다른 기기로 옮기거나 정기적으로 보관할 때는 암호화 백업 기능을 사용하세요. 백업에는 12자 이상의 별도 암호를 설정합니다. 백업 암호를 잃으면 복원할 수 없으므로 백업 파일과 다른 안전한 위치에 보관하세요.

화면의 백업 기능은 로그인한 상태에서 사용할 수 있습니다. 로컬 명령은 서버를 중지한 후 실행합니다.

```sh
npm run stop
npm run backup -- --output "백업 폴더/내 보관함.keydesk"
npm start
```

출력 폴더는 미리 만드세요. 소유자 비밀번호와 백업 암호를 차례로 입력합니다. 실제 파일을 다른 안전한 저장소에도 복사하고 정기적으로 별도의 테스트 데이터 경로에 복원해 보세요.

복원은 현재 데이터를 교체합니다. 먼저 현재 데이터의 백업을 만들고, 파일과 대상 데이터 경로를 확인하세요.

```sh
npm run stop
npm run restore -- --input "백업 폴더/내 보관함.keydesk"
npm start
```

복원에는 현재 대상 보관함의 소유자 비밀번호와 백업 암호가 필요합니다. 새 기기에서는 `setup` 후 첫 계정을 만든 다음 서버를 중지하고 복원하세요. 복원이 성공하면 기존 세션과 게이트웨이 클라이언트를 다시 설정해야 합니다. 잘못된 암호나 손상된 백업을 거부하면 기존 데이터가 유지됩니다.

## 비밀번호 재설정과 자동화

소유자 비밀번호를 잊었으면 서버 파일에 접근할 수 있는 로컬 계정으로 재설정하세요.

```sh
npm run stop
npm run reset-password
npm start
```

12자 이상의 새 비밀번호를 두 번 입력하면 기존 로그인 세션이 폐기됩니다. 이 명령을 실행할 수 있는 운영체제 계정은 보관함의 관리자와 같습니다.

자동화에는 `--password-file` 또는 `--password-stdin`을 사용합니다. 비밀번호를 명령줄 인수나 환경변수 값에 넣지 마세요. 입력은 UTF-8 JSON이며 PowerShell 5.1이 만드는 UTF-8 BOM도 허용합니다.

백업과 복원의 파일 형식:

```json
{ "ownerPassword": "현재 소유자 비밀번호를 여기에 입력", "password": "백업 암호를 여기에 입력" }
```

재설정의 파일 형식:

```json
{ "newPassword": "새 소유자 비밀번호를 여기에 입력" }
```

이 예시는 형식만 보여줍니다. 실제 암호는 비밀번호 관리자나 보호된 편집기에서 입력하세요. macOS와 Linux에서는 파일을 만든 뒤 `chmod 600 "비밀번호.json"`으로 권한을 제한하세요. Windows에서는 파일 속성의 보안 탭에서 자신의 계정만 읽도록 제한하세요. JSON 파일을 Git에 추가하지 말고 작업이 끝나면 삭제하세요.

```sh
npm run backup -- --output "내 백업.keydesk" --password-file "비밀번호.json"
npm run restore -- --input "내 백업.keydesk" --password-file "비밀번호.json"
npm run reset-password -- --password-file "새 비밀번호.json"
```

비밀 관리 프로그램이 JSON을 표준 출력으로 내보낼 수 있다면 파이프로 연결해 `--password-stdin`으로 전달할 수 있습니다. PowerShell 5.1의 비ASCII 파이프 인코딩 차이를 피하려면 한국어 암호에는 UTF-8 파일 방식을 사용하세요.

## 예약 백업과 보존 개수

`backup:scheduled`는 서버를 중지하지 않고 암호화 백업을 만듭니다. 서버가 꺼져 있어도 같은 명령을 사용할 수 있습니다. 기존 `keydesk.sqlite`와 `root-key`가 있어야 하며, 빈 경로에 새 보관함을 만들지 않습니다. 대화형 `backup` 명령의 중지 절차는 그대로 유지됩니다.

```sh
npm run backup:scheduled -- --directory "백업 보관함" --keep 7 --password-file "보호 폴더/백업 비밀번호.json"
```

`--keep`의 기본값은 7이며 1~365개를 지정할 수 있습니다. 현재 소유자 비밀번호와 백업 암호가 있는 앞 절의 JSON 파일을 사용하세요. 파일은 16KB 이하의 UTF-8 일반 파일이어야 합니다. 비밀번호 자체는 명령 인수와 작업 스케줄러 설정에 넣지 마세요.

JSON 비밀번호 파일은 평문이므로 파일 권한과 BitLocker, FileVault 또는 암호화된 Linux 저장소로 보호하세요. 백업 폴더와 별도의 보호 경로에 두고 Git·공유 폴더·일반 백업 대상에 포함하지 마세요. macOS와 Linux에서는 `chmod 600`을 적용해야 합니다. Windows에서는 상속된 일반 사용자 읽기 권한을 제거하고 실행 계정, SYSTEM과 Administrators만 읽을 수 있게 설정하세요. 예약 백업은 이 읽기 권한을 검사합니다. 소유자 비밀번호를 변경하면 JSON의 `ownerPassword`도 보호된 편집기에서 갱신하세요.

파일 이름은 `keydesk-scheduled-날짜시각-임의값.keydesk` 형식입니다. 명령은 생성한 암호문을 다시 읽고 고정된 백업 형식·암호 유도 설정과 인증 태그를 코어 암호화 함수로 검증합니다. 저장된 파일이 검증된 내용과 일치할 때만 보존 개수를 적용합니다. 백업 생성·암호 검증에 실패하면 이전 백업을 정리하지 않습니다.

정리는 위 이름 형식의 일반 파일에만 적용하며, 관련 없는 파일·디렉터리·심볼릭 링크는 남깁니다. 검증된 새 백업은 유지하고 나머지 파일 중 최신 이름 순서로 보존합니다. 보존 정리만 실패하면 새 백업을 유지하고 한국어 경고를 출력하므로 작업 로그도 확인하세요. 한 백업 폴더에는 한 보관함의 예약 백업만 저장하세요.

다음 예시는 운영체제에 등록할 내용을 설명합니다. Keydesk 설치가 일정을 자동으로 등록하지 않으며 이 안내에서 실제 작업을 생성하지 않았습니다. 먼저 같은 실행 계정으로 명령을 직접 실행하고 별도 데이터 경로에 복원해 확인하세요. 예약 작업에서는 Node 실행 파일·스크립트·데이터·백업·비밀번호 파일에 모두 절대 경로를 사용하세요.

### Windows 작업 스케줄러

작업 스케줄러에서 원하는 실행 계정과 매일 실행할 시각을 지정하세요. 동작의 프로그램은 `powershell.exe`, 인수는 다음 형식으로 지정합니다. 경로를 자신의 설치 위치에 맞게 바꾸세요.

```text
-NoProfile -NonInteractive -Command "$env:KEYDESK_DATA_DIR='D:\Keydesk 데이터'; & 'C:\Program Files\nodejs\node.exe' 'C:\Keydesk\tools\scheduled-backup.mjs' --directory 'D:\Keydesk 백업' --keep 7 --password-file 'D:\보호 폴더\백업 비밀번호.json'; exit $LASTEXITCODE"
```

시작 위치는 프로젝트 디렉터리로 지정하세요. 작업이 이미 실행 중이면 새 인스턴스를 시작하지 않도록 설정하고, 결과 코드와 작업 기록을 확인하세요. 실행 계정이 비밀번호 파일과 데이터 경로에 접근할 수 있어야 합니다.

### macOS launchd

예를 들어 `~/Library/LaunchAgents/local.keydesk.backup.plist`에 다음 구성을 작성할 수 있습니다. Node 위치는 터미널의 `command -v node` 결과를 확인해 바꾸세요. 아래 시각은 매일 로컬 시간 오전 3시입니다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>local.keydesk.backup</string>
  <key>ProgramArguments</key><array>
    <string>/opt/homebrew/bin/node</string>
    <string>/Users/사용자/Keydesk/tools/scheduled-backup.mjs</string>
    <string>--directory</string><string>/Users/사용자/Keydesk 백업</string>
    <string>--keep</string><string>7</string>
    <string>--password-file</string><string>/Users/사용자/보호 폴더/백업 비밀번호.json</string>
  </array>
  <key>EnvironmentVariables</key><dict>
    <key>KEYDESK_DATA_DIR</key><string>/Users/사용자/Keydesk 데이터</string>
  </dict>
  <key>StartCalendarInterval</key><dict>
    <key>Hour</key><integer>3</integer><key>Minute</key><integer>0</integer>
  </dict>
  <key>StandardOutPath</key><string>/Users/사용자/Keydesk 백업/예약.log</string>
  <key>StandardErrorPath</key><string>/Users/사용자/Keydesk 백업/예약 오류.log</string>
</dict></plist>
```

로그 폴더를 먼저 만들고 `plutil -lint`로 파일을 검사하세요. 경로와 권한을 확인한 뒤 원할 때 `launchctl bootstrap gui/$(id -u) "$HOME/Library/LaunchAgents/local.keydesk.backup.plist"`로 등록합니다. 이 예시는 해당 사용자 로그인 세션에서 동작합니다.

### Linux cron

`crontab -e`에서 실행 계정의 일정을 편집할 수 있습니다. 다음은 로컬 시간 오전 3시의 예시입니다. 로그 폴더를 먼저 만들고 Node 경로를 실제 절대 경로로 바꾸세요.

```cron
0 3 * * * KEYDESK_DATA_DIR='/home/사용자/Keydesk 데이터' /usr/bin/node '/home/사용자/Keydesk/tools/scheduled-backup.mjs' --directory '/home/사용자/Keydesk 백업' --keep 7 --password-file '/home/사용자/보호 폴더/백업 비밀번호.json' >> '/home/사용자/Keydesk 백업/예약.log' 2>&1
```

예약 시각에 기기가 꺼져 있으면 운영체제의 일정 정책에 따라 실행을 놓칠 수 있습니다. 주기적으로 백업 생성 시각, 경고 로그와 실제 복원을 확인하세요. 비정상 종료로 `.keydesk-scheduled.lock`이 남았다면 해당 폴더를 사용하는 예약 백업 프로세스가 모두 끝난 것을 확인한 뒤 잠금 디렉터리만 제거하세요.

## Docker 운영

Docker Engine과 Compose 플러그인 또는 Docker Desktop을 준비하세요. 이미지는 Node.js 26.12.1을 사용하며 일반 사용자로 실행합니다. 하나의 `keydesk-data` 볼륨에 루트 키와 데이터베이스를 함께 보관합니다. Compose는 호스트의 `127.0.0.1:8088`에만 포트를 공개합니다.

```sh
docker compose build
docker compose up -d
docker compose ps
docker compose exec keydesk node tools/manage.mjs setup --owner
```

마지막 명령은 컨테이너 내부의 로컬 연결로 소유자 계정을 설정합니다. 비밀번호를 두 번 숨김 입력하고 소유자 이름을 입력하세요. Docker의 포트 전달은 컨테이너의 로컬 연결로 인식되지 않으므로 첫 계정은 이 명령으로 만듭니다. <http://127.0.0.1:8088>에서 로그인하세요. 컨테이너를 다시 만들어도 이름 있는 볼륨은 유지됩니다. `docker compose down -v`는 영구 데이터를 삭제하므로 일반 중지나 업데이트에 사용하지 마세요.

```sh
docker compose stop
docker compose up -d --build
```

Docker에서 로컬 관리 백업을 실행할 때는 서비스를 먼저 중지하고 같은 볼륨을 사용하는 일회용 컨테이너에서 입력하세요. 파일은 영구 볼륨에 저장한 뒤 꺼낼 수 있습니다.

```sh
docker compose stop
docker compose run --rm keydesk node tools/manage.mjs backup --output /data/내백업.keydesk
docker compose up -d
docker compose cp keydesk:/data/내백업.keydesk ./내백업.keydesk
```

자동으로 첫 계정을 설정하려면 `setup --owner --password-stdin`에 `name`과 `newPassword`가 있는 JSON을 컨테이너의 표준 입력으로 전달하세요. 비밀번호 파일 방식을 쓸 때는 파일이 컨테이너 안에서 읽을 수 있는 경로에 있어야 합니다.

실제 파일을 꺼냈는지 확인한 뒤 볼륨 안의 사본을 필요에 따라 정리하세요. 화면에서 내려받는 암호화 백업도 사용할 수 있습니다.

AMD64와 ARM64는 같은 Dockerfile을 사용합니다. 맥미니의 Apple Silicon에서는 Docker Desktop이 ARM64 이미지를 빌드합니다. 여러 아키텍처의 이미지를 파일로 만들려면 Buildx를 사용하세요.

```sh
docker buildx build --platform linux/amd64,linux/arm64 --output type=oci,dest=keydesk-images.tar .
```

CI는 Linux·Windows·macOS 검사와 두 아키텍처 이미지 빌드를 구성합니다. 실제 실행 결과는 해당 CI 실행에서 확인하세요. 에뮬레이터의 이미지 빌드는 ARM64 장비에서 직접 사용한 결과와 다릅니다.

### 프록시와 인증서가 있는 빌드 환경

Docker의 기존 프록시 및 레지스트리 설정을 유지하세요. npm과 HTTPS의 인증서 검증을 끄지 마세요. 사내 또는 관리형 프록시가 별도 CA를 사용하면 BuildKit의 `proxy_ca` 비밀 마운트로 전달할 수 있습니다. 인증서는 이미지 계층에 복사하지 않습니다.

macOS와 Linux 예시:

```sh
docker build --secret "id=proxy_ca,src=$CODEX_PROXY_CERT" -t keydesk:local .
docker compose up -d --no-build
```

PowerShell에서는 `$CODEX_PROXY_CERT` 대신 `$env:CODEX_PROXY_CERT`를 사용하세요. Compose 자체로 빌드하려면 다음 내용을 로컬 `compose.proxy.yaml`에 작성하고 두 파일을 함께 지정하세요.

```yaml
services:
  keydesk:
    build:
      secrets:
        - proxy_ca
secrets:
  proxy_ca:
    file: ${CODEX_PROXY_CERT}
```

```sh
docker compose -f compose.yaml -f compose.proxy.yaml build
docker compose up -d --no-build
```

실행 중인 컨테이너도 별도 CA가 필요하면 인증서를 읽기 전용으로 마운트하고 `NODE_EXTRA_CA_CERTS`를 그 경로로 설정하세요. 빌드 비밀 마운트는 실행 컨테이너로 전달되지 않습니다.

## 게이트웨이만 외부에 공개하기

일반 REST 경로에서 인증값을 선택한 다음 **여러 인증 헤더·쿼리 설정**을 누르면 최대 8개의 인증 필드를 지정할 수 있습니다. 네이버 Maps처럼 두 키가 필요하면 각각 헤더로 추가하고, ODsay의 apiKey나 공공데이터의 serviceKey는 쿼리 파라미터로 지정합니다. KakaoAK처럼 접두어가 필요한 헤더는 접두어 칸에 입력합니다. 실제 키는 보관함에서 선택하며 필드 이름이나 기본 주소에 넣지 않습니다. 제공사에는 HTTPS 주소를 사용하세요.

먼저 로컬 보관함을 설정하고 필요한 제공사 키, 경로와 게이트웨이 클라이언트를 생성하세요. 각 클라이언트에는 필요한 프로젝트·경로만 연결하세요. 발급 직후 한 번 표시되는 토큰을 안전하게 보관하고 요청의 Bearer 인증으로 사용하세요. 토큰을 URL에 넣지 마세요.

`Caddyfile.example`은 Caddy를 Keydesk와 같은 호스트에서 실행하는 예시입니다. 실제 도메인의 DNS를 서버로 연결하고 Caddy의 HTTPS 인증서 발급 조건을 준비한 뒤 사용하세요. 예시의 도메인을 자신의 도메인으로 바꾸세요.

프록시는 `/gw/*` 경로만 Keydesk로 전달하고 관리 화면과 `/api/*`는 외부에서 차단합니다. Keydesk의 호스트 포트는 계속 루프백에 바인딩하세요. 관리 화면의 `KEYDESK_ORIGIN`은 로컬 주소로 유지하며 외부 게이트웨이 도메인으로 바꿀 필요가 없습니다. 다른 기기에서 관리하려면 신뢰할 수 있는 사설망이나 SSH 터널 등 별도의 접근 경로를 준비하세요.

Caddy를 별도 컨테이너로 실행하면 `127.0.0.1`은 Caddy 자신을 가리킵니다. 이 예시를 그대로 사용하지 말고 내부 네트워크의 서비스 주소로 연결하고, 외부로 공개하는 경로 제한을 유지하세요.

사용량이 확인되지 않은 호출은 0으로 간주하지 않습니다. 모델 단가와 원래 통화를 확인하고 원화 환산 환율·기준일을 설정하세요. 원화 금액은 추정치이며 제공사의 실제 청구액과 다를 수 있습니다. 토큰·비용 알림은 응답 후 측정치에 따른 경고로, 결제 상한을 보장하지 않습니다.

## 실행 상태 복구

`status`는 PID 존재만으로 정상 실행을 판정하지 않고 실행 관리자와 HTTP 응답을 확인합니다. 응답이 없다고 다른 프로세스를 강제로 종료하지 않습니다.

정상 중지는 `npm run stop`으로 수행하세요. 비정상 종료 후 실행 관리자가 응답하지 않는다면 운영체제의 프로세스 도구에서 해당 프로젝트 경로의 Node 프로세스가 남아 있는지 직접 확인하세요. 서버와 실행 관리자가 모두 종료된 것을 확인했을 때만 데이터 디렉터리의 `process.json`과 `.manage-lock` 디렉터리를 제거한 뒤 다시 시작하세요. `keydesk.sqlite`, `root-key`와 SQLite 보조 파일은 제거하지 마세요.

포트 사용 오류가 나면 다른 서버의 사용 여부를 확인하거나 `KEYDESK_PORT`를 변경하세요. `root-key` 누락 오류가 나면 서버를 중지하고 원래 키를 복구하세요. 새 키 파일을 임의로 만들어 기존 데이터베이스와 연결하지 마세요.
